# Project 2 Brief

> EDITING DIRECTIVE: DO NOT EDIT THIS FILE. IT IS THE AUTHORITATIVE PROJECT FRAME.

A client of the studio, a regional outdoor apparel retailer, has noticed that customers check the weather constantly but still misjudge what to wear. Raw numbers like "62°F, 40% chance of rain" don't turn into a decision. The client wants a "what to wear" weather visualizer that turns live conditions into clothing guidance anyone can read at a glance, in whichever style they find most intuitive.

Your job is to build a working prototype with your AI coding assistant, and to show your process while doing it.

Specifications:

- Configure a new repository in your GitHub account, and make an initial commit of the empty starting point before you build anything
- Build the prototype as a single self-contained `.html` file named `index.html` at the root of the repo. It must run locally by opening the file or using a simple local server, with no build step
- Pull live weather data from a free, keyless source such as Open-Meteo (`https://open-meteo.com`), and include the attribution its license requires
- Get the user's location from the browser location API, with a typed zip code or city as a fallback
- Show the same recommendation in three switchable styles:
  - **Text**: a plain-language summary (e.g. "Light jacket and an umbrella")
  - **Graphic**: icons or a diagram of the recommended items and the conditions driving them
  - **Character**: an illustrated figure dressed for the conditions
- Include an interactive timeline covering past, present, and future (e.g. a slider across the last several days through the next several). Moving it must update all three styles for the selected time
- Base recommendations on more than temperature: use at least feels-like, precipitation, and wind, with the rules easy to find and read in the code
- Handle failures gracefully: location denied, unknown city, network error
- Commit as you go, with at least one commit per major feature (each style, the timeline, error handling), and never commit an API key
- You must understand and be able to explain how your code works, not only that it runs

Deliverables:

- A functioning single-file HTML app meeting the specifications above
- The app published on GitHub Pages, with the live URL submitted (see instructions below)
- Your chat transcripts (showing a repository with real commit history)

Publishing to GitHub Pages:

1. Make sure your finished app is committed and pushed to GitHub as `index.html` at the root of the repo, on the `main` branch
2. Make sure the repo is public. GitHub Pages is free for public repos, while private repos need a paid plan
3. In the repo on GitHub, open **Settings → Pages**
4. Under **Build and deployment**, set **Source** to **Deploy from a branch**, then choose branch `main` and folder `/ (root)`, and click **Save**
5. Wait 1–2 minutes. Refresh the Pages settings screen until it shows "Your site is live at…" The URL will look like `https://<your-username>.github.io/<repo-name>/`
6. Open the URL in a browser and test it as a stranger would: location prompt, typed zip or city, all three styles, and the timeline. Fix anything that only works locally, then push again. Pages redeploys automatically within a minute or two of each push
7. Submit the live URL along with your repo link and transcripts

Publishing notes:

- A blank page or 404 usually means the file isn't named `index.html`, isn't at the repo root, or the site is still building
- The browser location API only works on secure pages, so it works on your Pages `https://` URL but may be blocked when opening the file directly from disk. Test both
- Anything in a public repo is public. Double-check that no keys or personal data are committed before you publish
